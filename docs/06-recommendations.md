# 06. Ядро продукта: модель рекомендаций

Это самая важная часть системы. Если рекомендации необъяснимы и не проверяемы,
продукт превращается в очередной «рыболовный календарь» из интернета. Поэтому модель
проектируется как **прозрачный скоринг на данных**, а не как набор магических if-else.

## 1. Что именно должна выдавать рекомендация

Для пары **точка + дата** (и опционально вида):

| Блок | Содержание |
|---|---|
| `score` | Оценка 0–100: насколько условия благоприятны |
| `label` | `отличный / хороший / средний / слабый / не стоит` |
| `species[]` | Вероятные виды с оценкой и кратким «почему» |
| `windows[]` | Часы повышенной активности (локальное время) |
| `tackle` | Оснастка, **поводок** (материал/диаметр/длина), крючок, груз/кормушка |
| `baits[]` | Наживки/приманки с приоритетом и размером |
| `groundbait` | Состав, фракция, стартовое количество, темп докорма (если применимо) |
| `tactics` | Проводка/техника, дистанция, глубина, направление заброса |
| `warnings[]` | Запрет, гроза/шторм, резкая смена давления, тонкий лёд |
| `explain[]` | Вклад каждого фактора: `factor`, `value`, `impact`, `text` |
| `confidence` | `low / medium / high` — зависит от полноты данных и числа отчётов |

Пример текста, который видит пользователь: *«87/100. Ключевые плюсы: вода 9 °C в оптимуме
для щуки, давление стабильное, ветер ЮЗ 4 м/с. Минус: полнолуние. Лучшие часы: 07:00–09:00
и 16:30–18:30. Поводок: флюорокарбон 0.40 мм, 25 см (или стальной 20 см под живца)»*.

## 2. Входные данные

1. **Погода и астрономия** — почасовой прогноз на дату: температура воздуха, давление
   (+ тренд за 6 и 24 ч), ветер (скорость, направление, порывы), облачность, осадки,
   восход/закат, фаза и освещённость Луны.
2. **Вода** — оценка температуры воды (модель или данные пользователей), тип водоёма,
   глубина, течение, прозрачность, уровень.
3. **Вид рыбы** — профиль повадок (см. [05](05-domain-model.md#22-инварианты-и-правила-целостности)):
   оптимальные температуры, сезонная и суточная активность, нерест, реакция на давление,
   предпочтения по свету, ветру, глубине.
4. **Локация** — история отчётов с этой точки (и в радиусе 3–10 км) за 7–14 дней:
   виды, снасти, наживки, успешность.
5. **Правила** — региональные запреты, ограничения снастей, минимальный размер.

## 3. Модель v1: взвешенный скоринг

```
score_day = clip( Σ_i (w_i · s_i) / Σ_i w_i · 100 , 0, 100 ) − penalties
score_hour(t) = score_day · (0.6 + 0.4 · activity_by_hour(t)) · light_bonus(t)
```

где `s_i ∈ [0,1]` — нормированная оценка фактора, `w_i` — вес (базовая калибровка ниже),
`penalties` — жёсткие ограничения (запрет, гроза, ураган, отсутствие данных).

### 3.1. Факторы и веса (базовая версия, экспертные)

| # | Фактор | Вес | Как считается `s` | Почему важно |
|---|---|---|---|---|
| 1 | Температура воды | **25** | трапеция: 1 в оптимуме вида, спад до 0 на границах диапазона | Сильнейший предиктор активности и распределения рыбы |
| 2 | Сезон / фенология | **15** | `activity_by_month[month]` из профиля, с поправкой на широту | Нерест, миграции, нагул |
| 3 | Давление и тренд | **15** | 1 при стабильном ±1.5 гПа/6 ч, спад при резких изменениях (|Δ|>6 гПа/6 ч → 0.2) | Резкие скачки выключают клёв на 1–2 дня |
| 4 | Ветер | **12** | скорость в допустимом диапазоне + «хорошее» направление (Ю, З, ЮЗ для умеренных широт) | Ветер перемешивает воду, создаёт кормовые зоны; сильный мешает ловить |
| 5 | Свежие отчёты локации | **12** | успешность и давность отчётов: `Σ exp(-age_days/4) · success` | Локальная правда важнее теории |
| 6 | Облачность / свет | **8** | оптимум по `light_preference` вида | Хищник активнее в сумерках и при облачности |
| 7 | Осадки | **8** | слабый дождь ≈ нейтрально/плюс, ливень — минус | Влияет на мутность и комфорт |
| 8 | Фаза Луны | **5** | 0.5–1.0, слабая модуляция; полнолуние/новолуние чуть выше для хищника | Наименее доказанный фактор — малый вес обязателен |
| | **Итого** | **100** | | |

Веса — **гипотеза для старта**, а не истина. Их надо калибровать на отчётах (раздел 7).

### 3.2. Жёсткие ограничения (не сумма, а отсечка)

| Условие | Действие |
|---|---|
| Действует нерестовый запрет для вида/водоёма | `score = 0`, `warnings += «запрет до …»`, `label = «не стоит»` |
| Гроза, шквал > 15 м/с, шторм | `score = min(score, 20)` |
| Ледяная корка/опасный лёд (зимой) | `score = 0` + предупреждение о безопасности |
| Нет прогноза на дату (за горизонтом) | `confidence = low`, данные не экстраполируются |
| Нет профиля вида | вид не рекомендуется, но показывается как «нет данных» |

### 3.3. Неполные данные

Пропущенный фактор **не заменяется нулём** (это несправедливо занижает оценку) —
вес перераспределяется пропорционально, а `confidence` понижается. Так `score` остаётся
сопоставимым между днями.

## 5. Выбор снасти, наживки и прикормки

Рекомендации по снастям — это **правила-данные**, а не код: таблица `recommendation_rules`
с условиями (`species`, `season`, `waterTemp`, `flow`, `depth`, `wind`, `isPaid`) и
приоритетом (чем уже условие, тем выше приоритет). Движок выбирает победителя и
склеивает результат.

### 5.1. Примеры правил (иллюстрация, требуют экспертного ревью)

| Вид / условие | Поводок | Крючок / груз | Наживка / приманка | Прикормка |
|---|---|---|---|---|
| Щука, осень, t воды 8–15 °C | Флюорокарбон 0.35–0.45 мм, 20–30 см; при живце/джерке — стальной 20–30 см | Офсет 2/0–4/0, джиг 10–20 г по глубине | Виброхвост/твистер 10–14 см, джеркбейт; живец | Не применяется |
| Судак, сумерки, t 12–20 °C | Флюорокарбон 0.25–0.30 мм, 30–40 см | Офсет 1/0–3/0, груз 10–24 г | Джиг 7–12 см, виброхвост, поролон | Не применяется |
| Лещ, фидер, t 15–22 °C | Флюорокарбон 0.12–0.16 мм, 40–70 см | Крючок 10–12, кормушка 30–60 г | Опарыш, червь, кукуруза, бутерброд | 1–2 кг: панировка + жмых + грунт; старт 5–8 кормушек, далее каждые 10–15 мин |
| Карп, пруд, t 18–25 °C | Флюорокарбон 0.25–0.35 мм, 15–25 см, волосяная оснастка | Крючок 4–8, груз 60–100 г | Бойлы, кукуруза, пеллетс | 2–5 кг: бойлы/пеллетс + кукуруза, привада за 12–24 ч |
| Карась, лето, t 18–26 °C | Леска 0.10–0.14 мм, 15–25 см | Крючок 12–14, поплавок 1–2 г | Червь, мотыль, тесто | 0.3–0.8 кг: панировка + жмых, малый старт |
| Окунь, t 10–20 °C | Флюорокарбон 0.14–0.18 мм, 20–30 см | Офсет/крючок 6–1/0, груз 3–10 г | Микроджиг 5–8 см, твистер, вертушка №2–3 | Не применяется |

Каждое правило обязано иметь: `conditions`, `output`, `source`, `reviewedBy`, `version`.
Выдача — с пометкой «рекомендация, не гарантия».

### 5.2. Как формируется текст совета

Шаблоны + подстановка: `«Поводок: {material} {diameter} мм, {length} см. Причина: {reason}»`.
Причина берётся из правила (например, «острые зубы щуки перерезают флюорокарбон тоньше
0.35 мм»). Это делает рекомендацию обучающей, а не приказной.

## 6. Окна активности и пример расчёта

1. Из почасового прогноза берутся `T(t)`, `P(t)`, `wind(t)`, `cloud(t)`, `precip(t)`.
2. Для каждого часа считается `s_i(t)` и `activity_by_hour[hour]`.
3. Сглаживание скользящим окном 3 ч, отсечение окон с `score_hour < 0.55 · max`.
4. Окна ограничиваются светлым временем и правилами (ночная ловля запрещена в регионе —
   окно отбрасывается с пояснением).

### Пример: щука, водохранилище, 25 октября

| Фактор | Значение | `s` | `w·s` |
|---|---|---|---|
| Температура воды | 9 °C (оптимум 8–15) | 0.95 | 23.75 |
| Сезон | октябрь, активность 0.90 | 0.90 | 13.50 |
| Давление | 1024 гПа, +1 гПа/6 ч | 0.85 | 12.75 |
| Ветер | ЮЗ 4 м/с | 0.95 | 11.40 |
| Отчёты локации | 3 за 4 дня, 2 успешных | 0.90 | 10.80 |
| Облачность | 60 %, сумерки | 0.80 | 6.40 |
| Осадки | нет | 0.80 | 6.40 |
| Луна | полнолуние, 14.5 сут | 0.60 | 3.00 |
| **Итого** | | | **88.0** |

→ `score = 88`, `label = «отличный»`, `confidence = high`.
Окна: 07:00–09:00 (пик 07:30–08:30) и 16:30–18:30.
Снасть: флюорокарбоновый поводок 0.40 мм × 25 см, офсет 3/0, джиг 14 г, виброхвост 12 см.
Предупреждений нет (запрет на щуку в октябре не действует).

Такие примеры (10–20 «золотых» кейсов от эксперта) становятся **регрессионными тестами
движка**: при изменении весов оценка не должна «уплывать» больше заданного допуска.

## 7. От данных к качеству: калибровка и проверка

### Этап 1 (MVP): экспертные веса + объяснимость
- Источник: профили видов, правила, доверие к отчётам.
- Проверка: golden-кейсы + ручная валидация экспертом.
- Метрика продукта: доля пользователей, отметивших «прогноз совпал» (thumbs up/down).

### Этап 2: статистическая калибровка
- Данные: отчёты с привязанным `weatherSnapshot` за 1–3 сезона.
- Модель: логистическая регрессия / gradient boosting на тех же факторах
  (target: `caught = 1`).
- Валидация: **временное** разбиение (обучение на прошлом сезоне, тест на следующем),
  чтобы не протекало будущее.
- Метрики: ROC AUC, Brier score, калибровочная кривая, precision@3 по видам.
- Внедрение: модель отдаёт `s`-функции или веса, но `explain` остаётся обязательным
  (SHAP/вклад факторов).

### Этап 3: персонализация
- Учёт снастей пользователя, его истории успехов, любимых техник.
- Ранжирование «что взять» под конкретный набор снастей.

### Ограничения и запреты
- Нельзя обучаться на данных без отрицательных примеров (`skunked`).
- Нельзя выдавать «прогноз улова» как гарантию; только вероятность/оценку условий.
- Веса Луны не повышать без статистического подтверждения: это главный источник
  ненаучных календарей.
- Любая версия модели должна быть воспроизводима по `inputsHash`.

## 8. Что тестировать в движке

1. `s_i` на границах: температура ниже/выше диапазона, ровно в оптимуме.
2. Сумма `w·s` = `score`; `breakdown` покрывает все факторы.
3. Перераспределение весов при пропуске данных (сумма весов = 100).
4. Жёсткие ограничения: запрет → 0; гроза → ≤20; лед → 0.
5. Окна активности: пустой прогноз, один час, окно на границе суток, смена часового пояса.
6. Golden-кейсы: 20 примеров с ожидаемыми оценками ±5 и ожидаемыми советами.
7. Выбор правила: приоритет более специфичного правила; отсутствие правила → честное
   «нет рекомендации» вместо выдумки.
8. Детерминизм: одинаковый вход → одинаковый выход (`inputsHash`).

## 9. Как это ложится на код

```
src/
  recommendations/
    recommendations.controller.ts   # GET /api/calendar, /api/recommendations
    scoring/                        # чистые функции s_i, агрегация
    rules/                          # загрузка правил из БД, приоритезация
    explain/                        # сборка человекочитаемого breakdown
  species/                          # профили видов (CMS + чтение)
  weather/                          # нормализованный прогноз (переписать текущий модуль)
  reports/                          # отчёты, модерация, агрегаты
```

Скоринг должен быть **чистыми функциями без I/O** — тогда его легко покрыть unit-тестами
и прогнать бэктест на исторических данных. Порядок внедрения — в
[08-roadmap.md](08-roadmap.md), целевая архитектура — в
[07-target-architecture.md](07-target-architecture.md).
