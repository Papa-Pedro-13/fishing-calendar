# 08. План развития

Оценки — в **человеко-днях** одного fullstack-разработчика, без учёта времени на
экспертное ревью контента (его нужно планировать параллельно). Диапазон отражает
неопределённость, а не «хорошо/плохо».

Статус на **22.10.2026**: этап 0 выполнен почти целиком (остались CI, Docker и починка
конфига ESLint), из этапа 1 сделаны нормализованная модель с маппером и базовый TTL-кэш.
ИИ-слой спроектирован (см. [06](06-recommendations.md)), но в коде не начат.
Детали и техдолг — в [04-implementation-status.md](04-implementation-status.md).

## 0. Логика приоритетов

1. **Сначала честность данных, потом фичи.** Календарь с неверной погодой и мусорной
   Луной хуже, чем его отсутствие.
2. **Сначала один сквозной сценарий**, потом ширина: один регион, 10–15 видов,
   календарь + карточка «что взять».
3. **Отчёты — не «соцсеть», а сигнал для алгоритма.** Их ценность в улучшении
   рекомендаций, поэтому сбор начинается сразу после календаря.
4. **Объяснимость — обязательное требование**, а не улучшение: без неё продукт
   не отличается от календарей из интернета.

`days=abc` → 400; на каждый день есть корректная фаза Луны; есть почасовые ряды;
справочники читаются из БД.

**Гейт:** до старта этапа нужны ответы на вопросы 1–3 из

## Этап 2. Календарь и ИИ-рекомендации (24–32 дня)

Конвейер: факты (погода, вода, вид, отчёты, правила) → детерминированный `score` и
ограничения → промпт → LLM → пост-валидация → гайд. Оценку и запреты считает код, модель
пишет и объясняет рекомендацию; без модели работает шаблонный фолбэк. Схема — в
[06-recommendations.md](06-recommendations.md).

| # | Задача | Приоритет | Оценка |
|---|---|---|---|
| 2.1 | Чистые функции скоринга (`s_i` по факторам) + агрегация + `penalties` | P0 | 4 |
| 2.2 | Движок правил (условия + приоритет + специфичность) для снасти/наживки/прикормки | P0 | 3 |
| 2.3 | Расчёт окон активности по часовому прогнозу и локальной таймзоне | P0 | 2 |
| 2.4 | `GET /api/v1/calendar?spotId&from&to&speciesId?` — дни, оценки, окна, объяснения | P0 | 2 |

| 2.6 | Предрасчёт календаря ночным job + инвалидация при обновлении прогноза/правил | P1 | 2 |

**Гейт ИИ-части:** до старта 2.10–2.13 нужны ответы на вопросы 8–10 из
[05-domain-model.md](05-domain-model.md#6-открытые-вопросы-нужны-решения-владельца-продукта)
(провайдер и бюджет, язык, контроль качества).

**DoD:** для тестовой точки календарь на 7 дней отдаёт оценки и окна; ИИ-гайд проходит
схему и guardrails на 20 golden-кейсах (0 нарушений запретов), сумма `breakdown` = `score`;
запрет вида обнуляет оценку с предупреждением; ответ < 300 мс из кэша; без LLM сервис
отдаёт `source=fallback`, а не ошибку; дневной бюджет соблюдается.

## 2. Метрики успеха

**Продуктовые**

| Метрика | Цель MVP | Как считать |
|---|---|---|
| Активация: посмотрел календарь → открыл карточку «что взять» | ≥ 40 % | события UI |
| Возврат D7 | ≥ 25 % в сезон | когорты |
| Доля оценок «прогноз совпал» | ≥ 65 % | thumbs up/down |
| Отчётов на 100 активных пользователей в месяц | ≥ 8 | БД |
| Доля точек с ≥ 3 отчётами за 14 дней | ≥ 30 % | агрегат |

**Технические (ИИ)**

| Метрика | Цель |
|---|---|
| Валидных гайдов по схеме | ≥ 99.9 % (после ретрая), иначе фолбэк |
| Нарушений guardrails в проде | 0 |
| Доля фолбэков без ИИ | ≤ 2 % |
| Кэш-хиты гайдов | ≥ 80 % |
| Стоимость одной рекомендации | в пределах `AI_DAILY_BUDGET_USD` |

**Технические**

| Метрика | Цель |
|---|---|
| p95 ответа календаря | ≤ 300 мс (кэш), ≤ 1.5 с (холодный) |
| Cache hit rate погоды | ≥ 90 % |
| Доля ошибок 5xx | < 0.5 % |
| Использование квоты провайдера | < 80 % с алертом |
| Покрытие скоринга тестами | 100 % ветвей факторов и ограничений |

## 3. Что сделать на этой неделе

1. Закрыть остаток этапа 0: починить конфиг ESLint (0.9), затем CI с `lint --no-fix` →
   build → unit → e2e (0.8) и Dockerfile. Без этого дальнейшие этапы снова будут
   проверяться вручную.
2. Зафиксировать ответы на открытые вопросы (регион MVP, горизонт прогноза, температура
   воды), утвердить схему фактов и гайда, выбрать LLM-провайдера и дневной бюджет.
3. Выбрать провайдера погоды на 7–14 дней.
4. Параллельно запустить контент: эксперт пишет 10–15 профилей видов и 20 golden-кейсов
   (в том числе эталонные гайды) — это самый длинный и наименее автоматизируемый путь.
5. Согласовать контракты `GET /api/v1/calendar` и `GET /api/v1/recommendations` до начала
   кодирования: они определяют и БД, и фронтенд, и промпт.
6. Довести погодный слой до этапа 1: интерфейс `WeatherProvider`, token bucket и
   stale-while-revalidate, почасовые данные для окон и фактов ИИ (1.7, 2.3).

## 4. Чего сознательно не делаем сейчас

- Микросервисы, Kubernetes, GraphQL.
- Обучение собственной модели и дообучение до накопления сезона отчётов — на старте
  используется готовая LLM через API.
- Соцсеть (лайки, комментарии, подписки на людей) — только отчёты и агрегаты.
- Мобильные нативные приложения — веб/PWA достаточно.
- Автоматический парсинг региональных правил — ручная сверка с источником надёжнее.
- Прогноз «сколько поймаешь» в килограммах — только оценка условий и вероятности.
